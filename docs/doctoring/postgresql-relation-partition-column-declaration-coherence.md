# PostgreSQL 18 relation-partition column declaration coherence

## Decision

`RelationPartitionSnapshot` composes direct declarative-partition membership with already-observed complete `pg_attribute.attidentity` and `pg_attribute.attgenerated` families when those families are present in the bounded `PostgresSchemaSnapshotV3`.

For every direct partition edge and same-named column:

- identity mode must match exactly: empty, `GENERATED ALWAYS`, or `GENERATED BY DEFAULT`;
- generated-column mode must match exactly: ordinary, stored generated, or virtual generated;
- generated expressions are deliberately not compared by this rule, because PostgreSQL permits a partition to use a different generation expression while requiring the generated status and stored/virtual kind to match.

If either optional catalog family was not observed, this successor does not invent it. The rule therefore preserves the distinction between unobserved evidence and observed source contradiction.

## Problem

The relation-partition successor already bound `pg_class.relispartition`, the direct `pg_inherits` parent edge, rowtype name/type/typmod compatibility, acyclic topology, and PostgreSQL 18 first-class NOT NULL inheritance. It did not compose the optional column identity or generation families across the same direct edge.

A fabricated bounded snapshot could therefore state that a partitioned-table parent column was `GENERATED ALWAYS AS IDENTITY` while the attached child was `GENERATED BY DEFAULT AS IDENTITY`, or that a stored generated parent column became virtual in the child, and still obtain governed relation-partition evidence.

Review `5214826228` records this P1 finding on exact head `725f0dbb5a0a2ce2c27a437c9e23cc23a0819903`.

## PostgreSQL 18 authority

Authority was checked against PostgreSQL 18 documentation and `postgres/postgres` `REL_18_STABLE@3d2e8573e9cb91bd2b545184f4f9b326d237bcd1`.

PostgreSQL 18 states that partitions inherit identity columns from the partitioned table, cannot have their own identity columns, and keep the properties of a given identity column consistent across the partition hierarchy.

For generated columns, PostgreSQL 18 requires a generated parent column's child to also be generated with the same kind (`STORED` or `VIRTUAL`), while allowing a different generation expression. If a parent column is not generated, its child must not be generated. `CREATE TABLE ... PARTITION OF` copies an omitted generated clause; `ALTER TABLE ... ATTACH PARTITION` insists that parent and child already match as to generated status.

Primary sources:

- PostgreSQL Global Development Group. (2026). *Identity Columns*. PostgreSQL 18 Documentation, §5.3.
- PostgreSQL Global Development Group. (2026). *Generated Columns*. PostgreSQL 18 Documentation, §5.4.
- PostgreSQL Global Development Group. (2026). *pg_inherits*. PostgreSQL 18 Documentation, §52.27.
- PostgreSQL Global Development Group. (2026). `REL_18_STABLE@3d2e8573e9cb91bd2b545184f4f9b326d237bcd1`.

## Alternatives considered

Comparing generated expression text was rejected. PostgreSQL explicitly permits different generation expressions across an inheritance or partition edge, so expression equality would turn a legal catalog state into a false negative.

Revalidating only at the independent `column_identity` or `column_generation` owner was rejected because those families do not own `pg_inherits` topology. The contradiction appears only when the already-observed families are composed with the direct partition edge, so `RelationPartitionSnapshot` is the minimal owning boundary.

Making identity/generation observation mandatory for every relation-partition snapshot was rejected. These are optional successor families and their absence must remain distinct from an observed-empty or observed-value family.
