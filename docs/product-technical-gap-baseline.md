### Collation coordinate, database encoding, provider shape, and effective definition

The historical qualified-name collation predecessor is intentionally preserved. Review `5203297768` established that namespace/name alone is insufficient to distinguish PostgreSQL `pg_collation` rows across encodings. The catalog-coordinate successor therefore preserves `(namespace, name, raw collencoding)` for each key; review `5203347945` extended the same coordinate proof to expression/predicate collation fields and relation-`Var.varcollid`. These predecessors remain valid as exact catalog-coordinate evidence for attached-index collation-OID equality inside one bounded catalog observation.

Review `5203629766` then established that coordinate equality is not source-usability proof. `IndexCollationDatabaseEncodingSnapshot` binds every modeled non-null collation to a PostgreSQL 18 `pg_database.encoding`, requiring `collencoding = -1` or the exact database encoding. The version-specific correction at review `5204368970`, RED `a3f877a65105dc7304d524e2fced2f65de83d6d7`, and production `15471cf7cb3639f2258b0d39950919fd9f7fad65` is current PostgreSQL 18 authority: encoding ID `7` remains `PG_MULE_INTERNAL`, and the valid backend/database range is `0..=34`.
