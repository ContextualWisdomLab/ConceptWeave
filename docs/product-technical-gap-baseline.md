The initial-privilege successor separates `pg_init_privs` from current `pg_proc.proacl`, preserves row absence versus presence and exact `privtype`, and retains the complete object-level initial EXECUTE ACL. PostgreSQL BUG #19483 and #19513 demonstrate a recovery defect in which `pg_init_privs.initprivs` still refers to a dropped role OID and a later dump/restore or `pg_upgrade` fails. Source Observation therefore preserves missing role lookups as unresolved nonzero raw OIDs instead of dropping the ACL entry, stringifying the OID as a role name, or rejecting the observation.

Review `5255771158` at exact pre-finding head `ae86019978a9d1fbce6b905d65df92835e851b39` found that this “complete ACL” contract was not actually represented after material construction. `IndexExclusionConstraintOperatorProcedureTransformConverterInitialPrivilegeMaterial::new` had hashed every ACL grant but discarded the grant vector, retaining only `privilege_type`, `grant_count`, dangling-role sets and an opaque digest. Structural RED `3d03f9b9d3ce27ae2d96732ec03780a345493afc` required immutable material readback; production repair `d406375f8989dae5dc06c50c1f4a776408a00bd8` retained the grant vector and added log-safe semantic accessors.

Review `5255912747` at exact pre-finding head `4967f12cb90ac41ec42263bfed47ba6bcbb49735` then found that the retained vector was still being sorted before hashing and storage. That normalization is not valid PostgreSQL semantics. PostgreSQL 18 `src/include/utils/acl.h` explicitly states that ACL array order matters to client utilities, particularly `pg_dump`, because grants with grant option must precede GRANTs that depend on them. PostgreSQL `pg_dump` also reads `pg_init_privs.initprivs` as the stored initial ACL baseline. Consequently, two source ACL arrays with the same entries in different order are not interchangeable recovery evidence. Structural RED `13e51561cac125f2a942e7ca0d0dd39433040426` requires swapped ACL arrays to produce distinct material digests and exact-sequence readback; production repair `966e2136c15aa049f72acfebf2c1a478d09c66ef` removed sorting.

Review `5256059436` at exact pre-finding head `50fff94eb567fd9b1c2150d4570ca1422acc9a60` found the remaining multiplicity loss: `Material::new` still rejected repeated identical ACL entries. PostgreSQL 18 `check_acl()` accepts one-dimensional non-null `aclitem[]` without imposing uniqueness, while `aclnewowner()` explicitly documents a state in which owner substitution creates duplicate ACL entries and contains dedicated merge logic. Observation is not normalization or remediation. Corrected structural RED `9747763c4b2370185bd18039b00e8ceaa9df206c` requires `[grant, grant]` to remain two source entries and to differ in digest from `[grant]`; production repair `55f828f6f6065fac89ae63f521d72d807f875c5b` removes source-level duplicate rejection. The earlier test-only `3ece5938...` is superseded because it contained a type-reference typo and is not evidence.

Earlier repairs established dangling-role representability, deterministic diagnostics, non-forgeable receipt-bound validation, exact canonical missing-role sets, complete routine Debug redaction, and readable ACL semantics. Grant, material, and validation `Debug` implementations intentionally omit raw role OIDs. Grant diagnostics retain PUBLIC/resolved/unresolved shape, resolved role names, and grant-option state; material/validation diagnostics retain counts and existing digest/provenance. Exact missing identifiers remain purpose-bound to explicit recovery-validation accessors. ConceptWeave still does not repair PostgreSQL catalogs or own role lifecycle.

Each initial ACL entry continues to distinguish PUBLIC, resolved role names, unresolved nonzero role OIDs, and exact grant option. Source array order and multiplicity are retained verbatim. OID zero remains invalid for unresolved-role constructors. A real role named decimal text such as `"16424"` remains distinct from unresolved raw OID `16424`. Sorted/deduplicated unresolved OID collections remain derived remediation sets only; they do not reorder or deduplicate the source ACL.

The PostgreSQL 18 `pg_init_privs` catalog declaration confirms that `(objoid, classoid, objsubid)` is the unique key and `initprivs` is forced non-NULL; `privtype` is not part of the unique key. ConceptWeave therefore retains row absence versus exactly one material rather than inventing simultaneous per-`privtype` rows for one object coordinate.

## Observation versus governance

Source Observation records exact external database state before policy. An initial ACL must remain inspectable evidence, not merely a digest commitment, and neither PostgreSQL array ordering nor multiplicity may be normalized away. The immutable material therefore retains the full source sequence while the digest commits sequence and repeated occurrences. A dangling `pg_init_privs` role reference is an observed recovery/security defect, not a reason to falsify the source by dropping the ACL entry or aborting observation. Canonical missing-role sets feed recovery validation; ordinary ACL semantics remain available without raw-OID disclosure.

The recovery validator consumes the owner-issued receipt, emits non-forgeable evidence retaining complete receipt provenance and exact purpose-bound missing-role identities, and blocks readiness whenever either set is non-empty. Typed recovery accessors expose exact role OIDs only on the recovery-validation surface; routine grant/material/validation `Debug` formatting redacts unresolved raw OIDs. ConceptWeave validates and governs publication. PostgreSQL catalog/role remediation remains outside this bounded context.
