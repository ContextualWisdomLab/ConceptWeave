### Collation coordinate, database encoding, provider shape, and effective definition

The historical qualified-name collation predecessor is intentionally preserved. Review `5203297768` established that namespace/name alone is insufficient to distinguish PostgreSQL `pg_collation` rows across encodings. The catalog-coordinate successor therefore preserves `(namespace, name, raw collencoding)` for each key; review `5203347945` extended the same coordinate proof to expression/predicate collation fields and relation-`Var.varcollid`. These predecessors remain valid as exact catalog-coordinate evidence for attached-index collation-OID equality inside one bounded catalog observation.

Review `5203629766` then established that coordinate equality is not source-usability proof. `IndexCollationDatabaseEncodingSnapshot` binds every modeled non-null collation to a PostgreSQL 18 `pg_database.encoding`, requiring `collencoding = -1` or the exact database encoding. The version-specific correction at review `5204368970`, RED `a3f877a65105dc7304d524e2fced2f65de83d6d7`, and production `15471cf7cb3639f2258b0d39950919fd9f7fad65` is current PostgreSQL 18 authority: encoding ID `7` remains `PG_MULE_INTERNAL`, and the valid backend/database range is `0..=34`. The superseded later-development-line `PG_UNUSED_1` attribution remains history only.

Review `5204669655` found that catalog-coordinate identity was being over-read as complete immutable collation-definition identity. PostgreSQL 18 stores behaviorally material state outside `(namespace,name,collencoding)`: `collprovider`, `collisdeterministic`, libc/provider locale fields, ICU rules, and recorded `collversion`. Source RED `542f0543e120ee733ec18136aa83ae4899db9721` requires identical catalog coordinates with different stored versions or provider semantics to remain distinct. Initial production `a7c53bee4a44ebbc1ef50ea5e1632d3dd7b99ac6` introduced the material-definition successor and export `a97d76547850b95f14ddb3cd853baaee36820381` exposed it.

Review `5204679813` found that stored `collversion` alone still misses an OS/ICU provider upgrade before catalog refresh. RED `7fb49690fc4a473917b1d038777cc05d443b1aa4` requires unchanged coordinate and stored version with a changed capture-time `pg_collation_actual_version(oid)` to produce distinct governed identity. Production `0a732e2ab011fa8b0e9ab04c3a1bc9da34e1be99` preserves both stored and actual provider versions, removes an unused-import warning, and includes both in the domain-separated definition digest. Focused contract `7a587443ed2e9b8547b67d6673bed60c8fc71846` exposes stored/current mismatch evidence explicitly. Decision record: `docs/doctoring/postgresql-index-collation-definition-version-integrity.md`.

Review `5204966516` then found that the material-definition constructor preserved provider fields without proving that their combination belonged to PostgreSQL 18's valid catalog vocabulary. RED `9601b4d11a87bbd5f8339524f9b30aca632b9ed1` pins impossible libc/non-libc field mixtures, non-ICU nondeterminism/rules, the PostgreSQL 18 built-in locale set, a valid ICU nondeterministic/rules case, and the bootstrap provider-`d` row shape. Production `e26f94b33aa9a89fdc6576c180dba29e6b65d4a9` validates those field invariants before `CollationDefinitionObservation` can be constructed or hashed.

Follow-up review `5205011408` closed the identity half of that same boundary. PostgreSQL 18 exposes provider `d` only through the bootstrap `pg_catalog.default` row (`collencoding = -1`), while user-created collations support builtin/ICU/libc providers. RED `0c1ed9930054d444b388cb54c157eb90f5fc6f9c` rejects provider-`d` observations at the wrong schema, name, or encoding. Production `f4dc329433443706e11526bce75e6bcb4892afff` binds provider `d` exactly to `(pg_catalog, default, -1)` before governed hashing. The effective behavior of that exact bootstrap row remains delegated to the separate database-default successor. Decision record: `docs/doctoring/postgresql-index-collation-provider-shape-integrity.md`.

Review `5204715861` closed the provider-`d` delegation seam. PostgreSQL 18 defines `pg_collation.collprovider = 'd'` as the database default, while the actual default definition is stored in `pg_database`: `datlocprovider` (`b/c/i`), `datcollate`, `datctype`, `datlocale`, `daticurules`, and recorded `datcollversion`. `pg_database_collation_actual_version(database_oid)` separately exposes the current provider version. Therefore the same used `pg_catalog.default` catalog coordinate/material row can refer to different effective default behavior in two source databases.

Compile RED `73464e2e8228a62bdae00555a1c24dd26ab66bd1` requires an unchanged recorded database version with a changed actual provider version, or a changed database-default locale, to change governed definition identity and rejects invalid `datlocprovider` tokens. Production `bf44d3dcdd83ffddb41314786becfacb9a007a71` adds `DatabaseDefaultCollationDefinitionObservation`, `PostgresDatabaseLocaleProvider`, and `IndexEffectiveCollationDefinitionSnapshot`; export `649c791301cb28137744cb290a2ee0a308144a98` exposes the successor. The constructor rebound-validates the exact material-definition predecessor, requires one database-default definition iff any bounded used collation has provider `d`, and rejects unrelated default evidence otherwise. Recorded/current database-default version mismatch remains explicit evidence rather than proof that dependent indexes were rebuilt. Decision record: `docs/doctoring/postgresql-database-default-collation-definition-integrity.md`.

Review `5204999247` found that this separate `pg_database` value object still admitted impossible locale/provider shapes. PostgreSQL 18 declares `datcollate` and `datctype` non-NULL, requires `datlocale = NULL` for libc and present for built-in/ICU, and rejects ICU rules for non-ICU providers. Source RED `3bdd7b26494dbe3688881d6ffcda94f9ff66c6bd` pins those nullability/provider invariants while retaining valid libc and ICU controls. Production `7e949f12de0ff959d31ca1e639d86cfdcbec2bd3` fails closed with `database_default_collation_provider_shape` before malformed database-default evidence can be hashed. Decision record: `docs/doctoring/postgresql-database-default-collation-provider-shape-integrity.md`.

Review `5205265135` then found a residual built-in database-locale hole in that value object: the built-in branch required only a present `datlocale`, so impossible PostgreSQL 18 built-in database locales such as `und`, `en-US`, or `ko-KR` could still enter governed effective-definition identity. Source RED `fba8e7849ae114df4fdfaf73bd6445a57ebb99a3` pins positive controls for `C`, `C.UTF-8`, and `PG_UNICODE_FAST` and rejects those invalid values. Minimal production repair `8efca49731b342e7f65ffb636b4a5a128c596674` constrains only the built-in branch of `validate_database_provider_shape()` to PostgreSQL 18's exact built-in locale vocabulary without changing issued predecessor or digest domains. Broader locale-versus-database-encoding compatibility remains deliberately outside this value object because encoding belongs to the composed predecessor/live adapter boundary. Decision record: `docs/doctoring/postgresql-database-default-collation-provider-shape-integrity.md`.
