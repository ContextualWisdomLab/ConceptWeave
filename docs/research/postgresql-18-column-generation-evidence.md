# PostgreSQL 18 column-generation evidence boundary

Status: Proposed / behavioral RED active

## Problem

The Source Observation successor preserves qualified column type, nullability, column collation, and identity declaration mode, but it does not preserve PostgreSQL `pg_attribute.attgenerated`. PostgreSQL 18 exposes three source-authoritative states: empty for an ordinary column, `s` for a stored generated column, and `v` for a virtual generated column. `pg_attribute.atthasdef` is insufficient because the same flag covers both default expressions and generation expressions; the catalog documentation explicitly directs consumers to `attgenerated` to distinguish them.

This is material semantic state. A stored generated column is computed on write and stored physically. A virtual generated column is computed on read and does not occupy normal column storage. PostgreSQL 18 also makes virtual generated columns the default generated-column kind. A generated column cannot simultaneously have an identity definition. Therefore otherwise-equal bounded column observations must not collapse ordinary, stored, and virtual generation modes into one governed source identity.

## Constraints

- `ColumnObservationV3` is a frozen compatibility contract and must not change meaning or digest framing.
- An adapter that did not capture `attgenerated` must remain distinguishable from one that explicitly observed `attgenerated = ''`.
- Catalog OIDs, rendered DDL, type names, defaults, `atthasdef`, or `pg_attrdef` text must not be used to infer generation mode.
- An observed generation family is complete for every bounded relation column, canonical under input permutation, and rejects duplicate exact column coordinates.
- Generation mode and identity mode remain independent source facts. If both families are observed, a generated column paired with `GENERATED ALWAYS` or `GENERATED BY DEFAULT` identity evidence is contradictory and fails closed.
- Generation-expression text is not part of this mode-only repair. A later immutable/versioned `pg_attrdef` expression family must preserve it explicitly before ConceptWeave can claim expression identity or dependency semantics.

## Alternatives

1. Add `attgenerated` directly to `ColumnObservationV3`. Rejected because it changes a frozen public value object and its legacy digest meaning.
2. Infer generation mode from `atthasdef`, defaults, or deparsed DDL. Rejected because `atthasdef` conflates default and generation expressions, while text reconstruction is not the direct catalog authority.
3. Add an optional, complete, domain-separated successor family. Selected because it preserves compatibility while making observed source truth explicit and independently versionable.

## Selected contract

Introduce `ColumnGenerationObservation` with exact schema, relation, relation kind, column coordinate, and one of three states: `not_generated`, `stored`, or `virtual_generated`. The public aggregate keeps the family unobserved on legacy constructors and exposes an explicit observed-family constructor/consuming method/accessor. The family extends source identity under a new domain separator only after coordinate/completeness/cross-family validation succeeds.

Canonical optional-family order should remain deterministic. The generation family belongs after source-authoritative column collation and before constraint timing/PERIOD evidence. Its relative position to column identity must be fixed by the implementation and both attachment orders must not create different identities for the same complete source facts; the simplest safe implementation is a single documented order with an explicit order error for the other path.

## Adapter obligation

When claiming this family, the PostgreSQL adapter must capture `pg_attribute.attgenerated` for every bounded column from the same bounded read-only catalog snapshot as the owning column evidence. Only the documented empty/`s`/`v` values are admitted; any unexpected value fails closed. `atthasdef` may indicate that a `pg_attrdef` row exists but does not substitute for `attgenerated`. The adapter must not deparse or infer a generation expression into this family.

A later generation-expression contract should bind the exact bounded column to the corresponding `pg_attrdef` expression and define canonicalization/provenance separately. That follow-on work must account for PostgreSQL 18 inheritance/partition rules, where generation status/kind must agree while generation expressions may differ.

## Risks and effects

The new family adds another optional digest layer and therefore increases constructor-order sensitivity if integrated carelessly. Production implementation must lock one canonical order and regression-test all already-supported family combinations that can coexist. The benefit is that semantic-layer discovery and immutable releases can distinguish write-time stored derivations, read-time virtual derivations, and ordinary columns without reconstructing truth from SQL text.
