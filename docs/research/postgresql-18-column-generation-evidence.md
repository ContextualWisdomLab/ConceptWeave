# PostgreSQL 18 column-generation evidence boundary

Status: Source repaired / exact-head acceptance pending

## Problem

The Source Observation successor must preserve PostgreSQL `pg_attribute.attgenerated`. PostgreSQL 18 exposes three source-authoritative states: empty for an ordinary column, `s` for a stored generated column, and `v` for a virtual generated column. `pg_attribute.atthasdef` is insufficient because the same flag covers both default expressions and generation expressions; the catalog documentation explicitly directs consumers to `attgenerated` to distinguish them.

This is material semantic state. A stored generated column is computed on write and stored physically. A virtual generated column is computed on read and does not occupy normal column storage. PostgreSQL 18 makes virtual generated columns the default generated-column kind. A generated column cannot simultaneously have an identity definition. Therefore otherwise-equal bounded column observations must not collapse ordinary, stored, and virtual generation modes into one governed source identity.

## Constraints

- `ColumnObservationV3` is a frozen compatibility contract and does not change meaning or digest framing.
- An adapter that did not capture `attgenerated` remains distinguishable from one that explicitly observed `attgenerated = ''`.
- Catalog OIDs, rendered DDL, type names, defaults, `atthasdef`, or `pg_attrdef` text are not used to infer generation mode.
- An observed generation family is complete for every bounded relation column, canonical under input permutation, and rejects duplicate exact column coordinates.
- Generation mode and identity mode remain independent source facts. If both families are observed, a generated column paired with `GENERATED ALWAYS` or `GENERATED BY DEFAULT` identity evidence is contradictory and fails closed.
- Generation-expression text is not part of this mode-only repair. A later immutable/versioned `pg_attrdef` expression family must preserve it explicitly before ConceptWeave can claim expression identity or dependency semantics.

## Alternatives

1. Add `attgenerated` directly to `ColumnObservationV3`. Rejected because it changes a frozen public value object and its legacy digest meaning.
2. Infer generation mode from `atthasdef`, defaults, or deparsed DDL. Rejected because `atthasdef` conflates default and generation expressions, while text reconstruction is not the direct catalog authority.
3. Add an optional, complete, domain-separated successor family. Selected because it preserves compatibility while making observed source truth explicit and independently versionable.

## Implemented contract

`ColumnGenerationObservation` records exact schema, relation, relation kind, column coordinate, and one of three states: `not_generated`, `stored`, or `virtual_generated`. Legacy constructors leave the family unobserved. `new_with_column_generations`, `with_observed_column_generations`, and `column_generations` expose the explicit observed-family boundary.

The family canonicalizes exact coordinates, rejects duplicates, requires complete coverage of every bounded relation column, and extends the governed source digest under `conceptweave.postgres_schema_snapshot.v3.column_generation.v1`. Generation evidence is attached after type/array and column-collation evidence and before column-identity, constraint-timing, or PERIOD evidence. Attempting to attach generation evidence after identity evidence fails as `column_generation_observation_order`, so attachment order cannot bypass cross-family validation.

When generation evidence is already present, attaching column-identity evidence fails as `column_generation_identity` if any exact bounded column is both stored/virtual generated and `GENERATED ALWAYS`/`GENERATED BY DEFAULT` identity. Explicit ordinary generation and explicit non-identity or identity state remain independent source facts; neither is inferred from the other.

## Adapter obligation

When claiming this family, the PostgreSQL adapter must capture `pg_attribute.attgenerated` for every bounded column from the same bounded read-only catalog snapshot as the owning column evidence. Only the documented empty/`s`/`v` values are admitted; any unexpected value fails closed. `atthasdef` may indicate that a `pg_attrdef` row exists but does not substitute for `attgenerated`. The adapter must not deparse or infer a generation expression into this family.

A later generation-expression contract should bind the exact bounded column to the corresponding `pg_attrdef` expression and define canonicalization/provenance separately. That follow-on work must account for PostgreSQL 18 inheritance/partition rules, where generation status/kind must agree while generation expressions may differ.

## Risks and effects

The new family adds another optional digest layer. The canonical attachment order is therefore part of the source-identity contract rather than an implementation convenience. Tests cover permutation-neutral family contents and reject the reverse identity→generation attachment path. Any future optional column family must either occupy one documented order or introduce a representation that makes order irrelevant without weakening existing digest compatibility.

The benefit is that semantic-layer discovery and immutable releases can distinguish write-time stored derivations, read-time virtual derivations, and ordinary columns without reconstructing source truth from SQL text. The repair does not claim generation-expression identity, dependency lineage, or runtime equivalence.
