# Changelog

All notable changes to ConceptWeave are documented here.

## Unreleased

### Added

- PostgreSQL partition key-constraint evidence now preserves exact `pg_constraint.conislocal` and `pg_constraint.coninhcount` in a domain-separated `IndexConstraintInheritanceSnapshot` layered over exact `conparentid` parentage. A parented primary-key or unique constraint requires `(conislocal=false, coninhcount=1)` while an unparented key constraint requires `(true, 0)`; negative counts fail closed. Inheritance receipts use a path distinct from parentage evidence, and no v3, relation-partition, index-partition, or parentage digest domain is rewritten.

- PostgreSQL key-constraint partition evidence now preserves exact resolved `pg_constraint.conparentid` in a domain-separated `IndexConstraintParentageSnapshot`. When an attached child index and its attached parent index both back observed primary-key or unique constraints, the child constraint must identify that exact parent constraint; a constraint-backed child index attached below a non-constraint parent index remains local with `conparentid = 0`. Frozen v3, relation-partition, and index-partition digest domains are unchanged.

- PostgreSQL attached partition-index constraint composition now rejects a structurally compatible child index when its attached parent index backs an observed primary-key or unique constraint but the child index backs no observed key constraint on its own relation. Standalone parent indexes remain standalone and no constraint is inferred from index shape; the repair composes only already-observed relation-local constraint/backing-index evidence and does not change an issued digest domain.

- PostgreSQL partitioned-index validity composition now requires every attached required local child index to report `pg_index.indisvalid = true` whenever its partitioned parent reports valid. Parent-valid/child-invalid governed tuples fail closed with `index_partition_child_validity`; fully attached all-valid hierarchies remain admitted, invalid-parent staging and stale-invalid-parent source states remain observable, the foreign-table exception is unchanged, and no issued digest domain changes.

- PostgreSQL partitioned-index topology now preserves the foreign-table child semantics implemented by PostgreSQL 18. A valid regular/non-unique partitioned index may omit a child index for a direct foreign-table partition because PostgreSQL skips local index creation there, while a valid unique partitioned index over such a foreign child fails closed with `index_partition_foreign_partition_unique`. Valid local table/partitioned-table children still require attached child indexes, invalid `CREATE INDEX ON ONLY` staging remains unchanged, and no issued digest domain changes.

- PostgreSQL column declaration evidence now rejects source-unreachable non-empty `pg_attribute.attidentity` and `attgenerated` states by relation kind before they enter governed successor identity. Identity and generated-column declarations are admitted on tables, partitioned tables, and foreign tables; views, materialized views, sequences, and composite types retain only catalog-empty declaration modes. A corrective PostgreSQL 18 source review fixed an earlier false negative that rejected foreign-table identity state. Explicit catalog-empty `not_identity` / `not_generated` observations remain valid for every modeled relation kind. The repair is covered by focused source contracts and does not change an issued digest domain.

- Declarative relation-partition evidence now composes optional complete column identity and generation families with each direct `pg_inherits` edge. Partition identity mode must match the partitioned-table parent exactly; generated-column ordinary/stored/virtual mode must match exactly while generation expressions may differ. Unobserved optional families remain unobserved, and predecessor/relation-partition digest domains are unchanged.

- Declarative relation-partition evidence now composes the optional complete `pg_attribute.attcollation` family with each direct `pg_inherits` edge. When column-collation evidence was observed, every child partition column must retain the exact resolved qualified collation identity of the matching partitioned-table parent column; an unobserved family remains unobserved. The repair uses the existing column-collation owner contract rather than copying collation truth into the partition aggregate, and no issued predecessor or relation-partition digest domain changes.

- PostgreSQL database-default libc C-UTF8 evidence now rejects source-unreachable database-encoding combinations before effective collation identity is admitted. `DatabaseDefaultCollationDefinitionObservation::validate_database_encoding` treats case-insensitive `C.UTF-8`/`C.utf8` in either `datcollate` or `datctype` as compatible with UTF8 and PostgreSQL's explicit superuser SQL_ASCII path, rejects LATIN1, and retains `C`/`POSIX` as encoding-independent controls. Arbitrary platform locale names are not inferred from spelling; no issued digest domain changes.

- PostgreSQL encoding-independent libc material-collation evidence now requires stored `pg_collation.collversion` to remain SQL `NULL` for raw `C/C/-1` and `POSIX/POSIX/-1` rows, including arbitrary-name `CREATE COLLATION ... FROM` copies. PostgreSQL 18 bootstrap rows have no stored version, the copy path cannot combine `FROM` with `VERSION` and recomputes a NULL actual version for C/POSIX, and `ALTER COLLATION ... REFRESH VERSION` cannot introduce a NULL↔non-NULL transition. Direct database-encoding libc C/POSIX collations with explicit `VERSION` remain representable; no digest domain is changed.

- PostgreSQL libc material-collation evidence now restricts encoding-independent `pg_collation.collencoding = -1` rows to the source-reachable raw locale pairs `C/C` and `POSIX/POSIX`. Arbitrary target identities created with `CREATE COLLATION ... FROM pg_catalog.C` or `... FROM pg_catalog.POSIX` remain valid because PostgreSQL copies provider/encoding/locale fields, while fabricated non-C/POSIX or mixed locale pairs fail closed. Concrete-encoding libc rows, catalog identity, and existing digest domains are unchanged.
- PostgreSQL ordinary built-in and ICU material-collation evidence now requires stored `pg_collation.collversion` presence. PostgreSQL 18 fills an omitted ordinary collation version from the provider's actual version for both direct creation and `CREATE COLLATION ... FROM`, while explicit `VERSION` remains valid stale/upgrade evidence. Libc/provider-`d` nullable semantics are unchanged, and the rule deliberately does not apply to database-default ICU `pg_database.datcollversion` because `template0` is a source-reachable NULL exception. No digest domain is changed.

- PostgreSQL copied-`ucs_basic` material-collation evidence now requires source-reachable built-in `C/6` rows to preserve stored `pg_collation.collversion = "1"`. PostgreSQL 18 `CREATE COLLATION ... FROM pg_catalog.ucs_basic` copies provider/encoding/locale but recomputes the omitted stored version from the built-in provider's fixed actual version `1`; missing or fabricated stored versions therefore fail closed. Direct built-in `C/-1` remains a separate creation path and can preserve operator-supplied `VERSION`; no digest domain is changed.

- PostgreSQL attached-index built-in `C` provider/encoding evidence now preserves source-reachable copies of bootstrap `pg_catalog.ucs_basic`. PostgreSQL 18 `CREATE COLLATION ... FROM` copies the source provider, locale fields, and raw `collencoding`, so built-in `C` is valid at `-1` for direct creation or at UTF8 encoding ID `6` for `ucs_basic`-descendant copies under their own catalog identities; unrelated encodings still fail closed. `C.UTF-8`, `PG_UNICODE_FAST`, ICU, and provider-`d` encoding rules remain unchanged, and no issued digest domain is changed.

- PostgreSQL database-default libc collation evidence now rejects fabricated non-NULL `pg_database_collation_actual_version(database_oid)` values for case-insensitive libc `C`, every `C.*` spelling, and `POSIX`, matching PostgreSQL 18 `get_collation_actual_version_libc()`. Those database defaults preserve NULL actual-version evidence; non-C libc locales keep platform-dependent optional version availability, and recorded `pg_database.datcollversion` remains independent. No digest domain is changed.

- PostgreSQL database-default built-in collation evidence now requires capture-time `pg_database_collation_actual_version(database_oid)` to be exactly `"1"` for `C`, `C.UTF-8`, and `PG_UNICODE_FAST`, matching PostgreSQL 18's built-in provider. Missing or fabricated current-version values fail closed while recorded `pg_database.datcollversion` remains independently nullable or stale drift evidence. Existing libc NULL-version and ICU non-NULL-version semantics remain provider-specific; no digest domain is changed.

- PostgreSQL ICU collation version evidence now requires capture-time actual provider versions wherever PostgreSQL 18 can construct valid ICU state. Ordinary ICU `CollationDefinitionObservation` and ICU `DatabaseDefaultCollationDefinitionObservation` reject missing `pg_collation_actual_version(oid)` / `pg_database_collation_actual_version(database_oid)` evidence, while recorded `collversion` / `datcollversion` remain independently nullable or stale so real drift is preserved. Libc `C`/`C.*`/`POSIX` keeps its valid NULL actual-version semantics; no digest domain is changed.

- PostgreSQL attached-index material-collation evidence recognizes bootstrap `pg_catalog.ucs_basic` as provider `b`, locale `C`, UTF8 `collencoding=6`, stored version `1`, and preserves the same source-reachable provider/locale/encoding tuple when PostgreSQL copies that row through `CREATE COLLATION ... FROM`. Directly created built-in `C` remains encoding-independent (`-1`); copied target identities remain distinct instead of being normalized to the bootstrap row.

- PostgreSQL built-in material-collation evidence now constrains capture-time `pg_collation_actual_version(oid)` to PostgreSQL 18's fixed built-in provider version `"1"` while preserving recorded `collversion` independently. Stale recorded values therefore remain observable as drift instead of being normalized away.

- PostgreSQL libc material-collation evidence now rejects impossible non-NULL capture-time provider versions for case-insensitive libc `C`, every `C.*` locale, and `POSIX`, matching PostgreSQL 18 `get_collation_actual_version_libc()`. An explicitly stored `collversion` remains representable with NULL actual version, preserving provider-version availability drift rather than erasing it.

- PostgreSQL database-default collation version evidence now binds the exact provider-`d` bootstrap row to the current database definition instead of allowing contradictory version sources. `CollationDefinitionObservation` rejects a stored `pg_collation.collversion` on exact `pg_catalog.default`, `IndexEffectiveCollationDefinitionSnapshot` requires the material default row's capture-time `pg_collation_actual_version(DEFAULT_COLLATION_OID)` evidence to equal the same bounded database observation's `pg_database_collation_actual_version(MyDatabaseId)`, and the material-row mismatch predicate delegates provider-`d` recorded-versus-actual drift to `pg_database.datcollversion` rather than treating the bootstrap row's structural NULL as drift. Existing digest domains and raw actual-version evidence remain unchanged.

- PostgreSQL ordinary non-default and database-default collation version evidence now treats provider-version availability changes as drift instead of reporting them as clean. `CollationDefinitionObservation::has_version_mismatch` preserves this rule for builtin/libc/ICU material collations, while `DatabaseDefaultCollationDefinitionObservation::has_version_mismatch` owns provider-`d` recorded/current drift. `Some/None` and `None/Some` are mismatches alongside differing `Some/Some`, while `None/None` and equal `Some/Some` remain clean in the layer that owns the recorded version. Existing digest domains and raw version evidence are unchanged; provider-specific construction rules remain stronger, so states PostgreSQL 18 cannot construct are still rejected.

- PostgreSQL attached-index material-collation evidence now binds provider/locale semantics to source-reachable `pg_collation.collencoding`: direct built-in `C` is encoding-independent (`-1`), UTF8 built-in `C/6` can also arise through copies of `pg_catalog.ucs_basic`, built-in `C.UTF-8` and `PG_UNICODE_FAST` use UTF8 encoding ID `6`, and ICU is encoding-independent (`-1`). `CollationDefinitionObservation` rejects impossible provider/catalog-encoding tuples with `index_collation_definition_provider_encoding` before governed hashing; the broader source-database usability predecessor remains unchanged for libc and source binding.

- PostgreSQL database-default collation evidence now composes the built-in locale vocabulary with the exact source `pg_database.encoding`: built-in `C` remains valid across supported backend encodings, while PostgreSQL 18 `C.UTF-8` and `PG_UNICODE_FAST` require UTF8. `DatabaseDefaultCollationDefinitionObservation::validate_database_encoding` is invoked by `IndexEffectiveCollationDefinitionSnapshot` against the existing database-encoding predecessor before effective evidence can be hashed, so non-UTF8 + UTF8-only built-in locale tuples fail closed without changing predecessor digest domains.

- PostgreSQL database-default ICU evidence now mirrors PostgreSQL 18's exact backend-encoding support table before effective evidence is hashed. `DatabaseDefaultCollationDefinitionObservation::validate_database_encoding` rejects ICU with SQL_ASCII, EUC_JIS_2004, MULE_INTERNAL, LATIN10, or WIN874 while retaining every backend encoding that `REL_18_STABLE/src/common/encnames.c::pg_enc2icu_tbl` marks supported. The rule composes with the existing `IndexCollationDatabaseEncodingSnapshot`; it does not infer raw catalog values or change any issued digest domain.

- PostgreSQL database-default collation evidence now validates PostgreSQL 18 `pg_database` locale/provider shape before construction: `datcollate` and `datctype` evidence are required for every provider, libc requires `datlocale = NULL`, built-in/ICU require `datlocale`, ICU rules are rejected for non-ICU providers, and the built-in provider accepts only PostgreSQL 18's `C`, `C.UTF-8`, or `PG_UNICODE_FAST` database locale identifiers. Malformed database-default state therefore cannot be hashed into `IndexEffectiveCollationDefinitionSnapshot`.

- PostgreSQL attached-index material-collation evidence now fails closed on impossible PostgreSQL 18 provider/field shapes before they can be hashed. `CollationDefinitionObservation` enforces libc `collcollate`/`collctype` versus provider-locale separation, limits nondeterministic definitions and ICU rules to ICU, restricts built-in locale identifiers to PostgreSQL 18's `C`, `C.UTF-8`, and `PG_UNICODE_FAST`, and binds provider `d` exclusively to the bootstrap `(pg_catalog, default, collencoding=-1)` row with its deterministic no-locale shape. Existing collation digest domains remain unchanged; live catalog extraction/differential acceptance remains transport work after representation GREEN.

- PostgreSQL attached-index collation evidence now closes database-default provider delegation with a domain-separated effective-definition successor. When any bounded used `pg_collation` row has `collprovider = 'd'`, `IndexEffectiveCollationDefinitionSnapshot` requires one exact `pg_database` default definition preserving validated `datlocprovider`, raw nullable `datcollate`/`datctype`/`datlocale`/`daticurules`, recorded `datcollversion`, and capture-time `pg_database_collation_actual_version(database_oid)`; the same evidence is rejected as unrelated when no used collation delegates to provider `d`. Locale or actual-provider-version changes therefore alter governed identity even if the used `pg_catalog.default` coordinate and material `pg_collation` row remain unchanged. Recorded/current mismatch remains observable and is not treated as proof that dependent indexes were rebuilt.

- PostgreSQL attached-index collation evidence now has a domain-separated material-definition successor above the catalog-coordinate and database-encoding proofs. `CollationDefinitionObservation` preserves provider, deterministic mode, raw nullable libc/provider locale fields, ICU rules, recorded `pg_collation.collversion`, and capture-time `pg_collation_actual_version(oid)` separately, so an OS/ICU provider upgrade cannot leave governed identity unchanged merely because `(namespace,name,collencoding)` and the stored version have not yet changed. `IndexCollationDefinitionSnapshot` rebound-validates exact predecessor digests and provenance, requires exactly one definition for every distinct non-null collation used by key/expression/predicate/relation-`Var` evidence, and fails closed on missing, duplicate, or unrelated definitions. Stored/current version mismatch remains observable and is never normalized into proof that affected indexes were rebuilt. Concrete PostgreSQL extraction and provider-version live differential remain transport work after representation GREEN.

- PostgreSQL attached-index collation evidence now has a domain-separated source-database encoding successor. Exact per-key and expression/relation-`Var` catalog-identity predecessor digests remain immutable while `PostgresDatabaseEncodingObservation` mirrors the PostgreSQL 18 `REL_18_STABLE` backend-valid encoding domain: IDs `0..=34` are server/backend encodings, including `PG_MULE_INTERNAL == 7`, while client-only/sentinel/negative values are rejected. `IndexCollationDatabaseEncodingSnapshot` requires every modeled non-null `pg_collation.collencoding` to be `-1` or the exact observed `pg_database.encoding`. A follow-up correction removed a future-PostgreSQL `PG_UNUSED_1` assumption that had been projected backward into the v18 contract. Concrete `pg_database.encoding` extraction and live differential acceptance remain transport work after representation GREEN.

- PostgreSQL attached-index collation equality now has domain-separated catalog-identity successors. Per-key `pg_index.indcollation`, modeled expression/predicate collation fields, and relation-`Var.varcollid` retain their historical qualified-name predecessors while new evidence preserves exact namespace/name/raw `pg_collation.collencoding`, rejects same-qualified-name/different-catalog-row parent/child pairs, composes with the existing whole-tree equality proof, and never rewrites issued digests. Concrete PostgreSQL OID resolution and live attachment differential acceptance remain transport work after representation GREEN.

- PostgreSQL relation/index-partition evidence now uses domain-separated immutable successors for direct partition topology and attachment-definition semantics. Mapped key/`INCLUDE` structure, collations, resolved operator families, exclusion operator/procedure/strategy tuples, and canonical expression/partial-predicate semantic trees are validated against the exact predecessor stack without rewriting frozen v3 identity. Relation-local expression Vars use stable column identity instead of physical attribute numbers, OID-backed semantic identities resolve to qualified signatures, and direct-child whole-row references fail closed. The live PostgreSQL semantic-tree extractor and differential oracle remain open before end-to-end source acceptance; raw `pg_get_expr`, `pg_node_tree`/`nodeToString`, or reconstructed DDL are not semantic substitutes.

- Declarative relation-partition evidence now rejects missing/extra child columns and same-named columns whose qualified PostgreSQL type differs from the parent while allowing PostgreSQL's valid name-based mapping across different physical column ordinals. A domain-separated structured `pg_attribute.atttypmod` successor now preserves complete raw signed `int4` evidence per bounded column, rebound-validates the exact predecessor stack, requires direct parent/child modifier equality, and issues exact receipts without rewriting frozen v3 or relation-partition identity. The concrete PostgreSQL adapter and live differential acceptance for this evidence remain open.

- Relational evidence now distinguishes unique constraints that treat missing values as distinct from those that treat them as equal, while retaining unknown behavior when it was not observed. Evidence identity changes with that behavior; earlier evidence is not rewritten.

- PostgreSQL schema snapshots now carry a v3 successor representation alongside the existing v2 form. Relations retain their observed kind, source comment, and relation-scoped index evidence (key and `INCLUDE` attribute roles with expression positions kept structurally distinct, uniqueness, `NULLS NOT DISTINCT`, access method, readiness/validity/liveness, exact partial predicate, exact server-rendered `pg_get_indexdef` text, and comment), schema-scoped domain and enum observations join the same authorized schema allowlist as tables, and column type bindings and domain base types resolve by exact qualified name without consulting `search_path`. Relation-level and relation-child successor coordinates carry the exact `pg_class.relkind` (`/schemas/{schema}/relations/{kind}/{name}/...`) so views, materialized views, foreign tables, sequences, and composite types are never mislabelled with table vocabulary, and a receipt cannot be satisfied by a differently-kinded relation of the same name. Index attribute roles must agree with their key/include collection, the combined positions must be contiguous with the key positions first, and `INCLUDE` accepts only simple columns, so contradictory or expression-carrying index layouts fail closed. The v3 identity is domain-separated from v2, so equal object sets never collapse the two generations into one digest, and unknown or ambiguous type bindings fail closed.

### Security

- Model-generated semantics remain non-authoritative until deterministic validation and authorized review.
- Source Observation rejects authorization-metadata budget requests above the canonical provider-independent hard caps before registry/database access, preventing callers from minting an effectively unbounded retained schema-selection envelope; source policy then separately admits only an equal-or-narrower complete resource envelope.
- Source Observation structurally rejects schema-selection metadata outside the caller-requested count/byte envelope before registry/database access, then separately requires trusted local policy to admit that metadata envelope together with operation/statement/row/byte/concurrency ceilings.
- Source Observation adapter execution now requires a registry-authorized request envelope; a well-formed opaque key alone cannot cross the canonical execution seam, and credential material remains adapter-local.
- Source Observation schema scope is policy-authorized, not caller-self-authorized: source-key recognition alone defaults to deny schema access, exact requested names are checked without case/Unicode normalization, and snapshot construction independently rejects locally observed schemas outside the authorized request.
- Source Observation resource ceilings are policy-authorized, not caller-self-authorized: source+schema authorization alone defaults to deny the complete `ObservationResourceEnvelope`; wider-than-policy requests fail with `UnauthorizedResourceEnvelope` before adapter/source/snapshot side effects.
- Source Observation source identity is policy-bound, not mutable-key-bound: missing/invalid connection-policy bindings fail closed, stale bindings must be rejected before source access, and immutable snapshot/receipt provenance retains the authorized binding separately from the content digest.
- Source Observation immutable snapshot construction retains the full authorized schema scope; an adapter cannot mint canonical digest/receipt evidence for a locally observed table outside the request's exact schema allowlist.
- Source Observation authorization consumes the same monotonic operation budget as adapter execution; source lookup, binding, schema and resource policy work consume that budget, later policy stages are not started after expiry, and adapters receive only the remaining duration rather than a reset timeout.
- Source Observation authorization is single-use at the canonical execution seam: the authorized request cannot be cloned and is consumed by `observe`, so retries must re-authorize rather than replay one grant and multiply resource consumption.
- Client authoritative-use admission rejects incompatible, unpublished, or non-authoritative releases without requiring a network/model call.
- Legacy compatibility is explicit opt-in policy; unknown versions remain fail-closed and the current version cannot also be configured as legacy.
- Release diff validates both compared releases through the same fail-closed authoritative-use gate so comparison cannot bypass contract-version, publication-state, or truth-status policy.
- Detached-artifact integrity verification first applies authoritative-use admission, then computes SHA-256 over the exact supplied detached semantic-artifact bytes and rejects any mismatch with the declared release digest.
- Digest syntax validation remains distinct from byte verification so a syntactically valid digest is never treated as proof that detached artifact content matches it.
- Supersession validation requires exact predecessor/successor id-and-digest references and leaves the prior published release immutable; a correction is not inferred from ordering, timestamps, or semantic similarity.
- Unsafe Rust is forbidden in the core domain, client, source-observation, and source-port contract crates.
